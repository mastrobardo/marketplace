# W12-T21 — Translations are data, not code

- **Slice**: S10 Design system (`agent-ui`) — i18n is this slice's (`TODO.md` §4)
- **Decides**: what format the translation catalogues live in, and what guards them once they are
  no longer TypeScript.
- **Supersedes**: `W0-T04`'s catalogue format, and the i18n half of `W0-T23`'s design (§4).

---

## 1. Purpose

> translations should go on jsons. Which, in a future, might come from some online service. Having
> them in the code is a nogo.
> — operator, 2026-09-20

`es.ts` and `en.ts` become `es.json` and `en.json`. That is the whole change; §2 is what it costs and
what replaces it.

## 2. Design

### 2.1 The compile-time key union is removed, deliberately, and it would have worked

`W0-T04` built three enforcement mechanisms on the catalogues being TypeScript:

1. `TranslationKey = keyof typeof es` — a literal union of every key.
2. `en.ts` carrying `satisfies Translations` — a missing key is a compile error naming it, an extra
   key an excess-property error.
3. `t(key: TranslationKey)` — an unknown key at a call site does not compile.

**All three survive a JSON module.** TypeScript infers literal keys from JSON under
`resolveJsonModule`, which this repo already sets, and `moduleResolution: Bundler` means a plain
`import es from './es.json'` with no import attribute. A two-way `Exact<keyof typeof es, keyof typeof
en>` assertion reproduces the parity check. This was **verified against `tsc` before being rejected**,
because "we removed it" and "it could not be kept" are different facts and the second one is false.

It is removed because of the premise behind the move. **If the catalogue is going to be owned by a
translation service, its keys are not knowable at compile time.** A union derived from the snapshot
checked into this repo is true exactly until the first fetch, and every call site typed against it
would then be claiming a guarantee nothing can honour. It would also re-couple the translations to
the code in the change whose purpose is to free them.

That is `MEM-2026-09-20-29` — *build it when a feature needs it, never in anticipation* — read in the
other direction: **do not keep a mechanism whose premise you are in the act of removing.**

Operator, 2026-09-20: *"It is fine to have extensive guards and typechecks, but this is not one of
those occasions."*

### 2.2 What guards a missing translation now

Nothing new was written for this. Three things already existed and do not care where the catalogue
came from:

| Guard | Catches | Where |
|---|---|---|
| Key-set parity | a key in one language and not the other | `tests/i18n.test.ts` |
| Non-empty string per key | a key present but blank | `tests/i18n.test.ts` |
| `missingKeyHandler` **throws** | an unknown key reaching `t()` at runtime | `src/i18n/index.ts` |

The first two run against the real catalogues and will still run when those are fetched rather than
imported, which is more than the compile-time mechanism could say. What is genuinely lost is the
*moment* of feedback: a typo is now caught by the suite rather than by the editor.

### 2.3 What else goes with it

- **Three fixture projects** — `tests/fixtures/{valid,unknown-key,incomplete-catalogue}` — and the
  three tests that shelled out to `tsc` to prove mechanism 1 and 2. They tested the mechanism this
  ticket removes; keeping them would mean keeping it. The web suite drops from **16.6s to 5.3s** as a
  side effect: each of those had a 120s timeout and a full `tsc` run behind it.
- **Section comments.** JSON has none. The dotted key prefixes (`job.quotes.*`) already group them,
  and a `_comment` key would be a translatable string that is not a translation.
- `TranslationKey` **stays as a name**, aliased to `string`. `features/auth/schema.ts` maps validation
  failures to keys and means something by it; rewriting eleven call sites to bare `string` would lose
  that and gain nothing.

## 3. What does not change

- **Flat dotted keys.** `nav.home` is one key, not `home` under `nav`, so `keySeparator: false` and
  `nsSeparator: false` stay exactly as they are.
- **Spain first.** `es` is still the first locale, the default and the fallback.
- **Every value.** The JSON was generated by importing the TypeScript modules and serialising them,
  not by transcription, so all 220 keys carry byte-identical values.

## 4. What this leaves broken for somebody else

**`W0-T23`'s i18n half no longer has a design.** That ticket exists because seven slice agents append
to two catalogue files and git cannot merge that cleanly — *"a key dropped in a merge is a compile
error at best and a missing translation shipped to a user at worst."* **The problem is untouched by
this ticket and is now slightly worse:** JSON has no comments to anchor a merge and stricter comma
rules than TypeScript.

Its proposed solution is void. `W0-T23` §4 preserves `TranslationKey` as *"a union of literal key
names, composed as `keyof typeof es`"* and `en/index.ts` carrying `satisfies Translations` — both
removed here. A namespaced split is still possible (one JSON file per slice, merged at load), but it
must be re-argued rather than inherited, and the arrival of a translation service may moot it
entirely by taking the files out of the repo. Flagged, not solved.

## 5. Acceptance criteria

- **AC1** — `es.json` and `en.json` exist; `es.ts` and `en.ts` do not.
- **AC2** — Both catalogues have identical key sets and no empty values.
- **AC3** — Every value is byte-identical to what the TypeScript module held.
- **AC4** — The app builds, typechecks and renders in both languages with no key changes.
- **AC5** — An unknown key at runtime throws rather than rendering the raw key.
- **AC6** — No source file imports `i18n/locales/*.ts`; `TranslationKey` comes from `i18n/index.ts`.
- **AC7** — The three compile-failure fixtures are gone, and `tsconfig.json` no longer excludes them.

## 6. Out of scope

- **Loading translations over HTTP.** Nothing fetches a catalogue yet; this ticket only removes the
  obstacle to it. Building the fetch now would be the empty promise in the other direction.
- **Splitting the catalogues per slice** — `W0-T23`, whose design this invalidates (§4).
- **A translation service, a TMS export, or a locale beyond `es`/`en`.**
