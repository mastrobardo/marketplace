## Log

- 21:30 operator, 2026-09-20: *"translations should go on jsons. Which, in a future, might come from
  some online service. Having them in the code is a nogo."*

- 21:35 **proposed keeping the compile-time key safety through `keyof typeof esJson`, and the
  operator rejected it.** *"why keyof typeof json? It is fine to have extensive guards and
  typechecks, but this is not one of those occasions."* They are right, and the reason is their own
  premise: if the catalogue is going to come from a service, its keys are **not knowable at compile
  time**, so a union derived from the checked-in snapshot is true only until the first fetch. It
  would also re-couple translations to the code in the very change meant to free them — which is
  `MEM-2026-09-20-29`'s empty promise, applied to a type rather than to a column.

  Verified before conceding that the mechanism *would* have worked (`keyof typeof es` does yield a
  literal union from a JSON module under `moduleResolution: Bundler`, and a two-way `Exact<>` check
  does catch key drift). It works and is still wrong, which is worth recording separately from
  "it cannot be done".

- 21:40 **what actually guards this is already in `tests/i18n.test.ts`** and predates the change:
  key-set parity between the two catalogues, every value a non-empty string, and `missingKeyHandler`
  throwing on an unknown key rather than rendering it. The compile-time machinery was largely a
  second copy of checks that run on real data anyway.
